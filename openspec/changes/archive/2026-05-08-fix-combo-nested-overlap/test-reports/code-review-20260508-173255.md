### Warnings (WARN)

#### [WARN-1] packages/rust/src/layout.rs:293-306
- **Category**: Logical Error / Boundary Handling
- **Description**: The nearest-neighbor `nearest_dx`/`nearest_dy` calculation produces incorrect direction signs when rectangles are overlapping. When `xi < xj` (i is left of j), the formula `(ri.left + ri.width) - rj.left` computes the gap between the right edge of i and the left edge of j. When rectangles overlap, this value is **positive** (right edge of i extends past left edge of j). However, the intended semantic is that the direction should push i **further left** (negative dx), but the computed `nearest_dx` is positive. The code then falls through to `dx = nearest_dx` when `abs > 1e-6`, which means when overlapping, `dx` becomes positive instead of the correct negative (push i left, push j right). This is the opposite of the intended separation direction.

  Specifically: when two rects overlap horizontally with i to the left of j, the center-to-center `xi - xj` is negative (i's center is left of j's center), which correctly pushes i left and j right. But `nearest_dx = (ri.left + ri.width) - rj.left` is positive when overlapping, reversing the direction and pushing them **together** instead of apart.

  In practice this may be masked because `dist = sqrt(dx^2 + dy^2)` remains positive and the `move_amount` includes a large `+ GAP` that may overcome the direction reversal in many cases. But the directional component is semantically inverted for overlapping rects, and this could cause oscillation or failed convergence in certain configurations.
- **Suggestion**: When rectangles overlap, the nearest-neighbor gap is negative (edges cross). The sign of `nearest_dx`/`nearest_dy` should match the center-to-center direction. Consider either: (a) using center-to-center direction always (the original code) while using nearest-neighbor distance only for magnitude, or (b) ensuring the sign of the nearest-neighbor vector matches the center-to-center sign. For example:

  ```rust
  let center_dx = xi - xj;
  let center_dy = yi - yj;
  // Use nearest-neighbor for magnitude, center-to-center for direction
  let nearest_dist_x = if xi < xj {
      rj.left - (ri.left + ri.width) // gap (negative when overlapping)
  } else {
      ri.left - (rj.left + rj.width)
  };
  let nearest_dist_y = if yi < yj {
      rj.top - (ri.top + ri.height)
  } else {
      ri.top - (rj.top + rj.height)
  };
  let dx = if nearest_dist_x.abs() > 1e-6 {
      center_dx.signum() * nearest_dist_x.abs()
  } else {
      center_dx
  };
  let dy = if nearest_dist_y.abs() > 1e-6 {
      center_dy.signum() * nearest_dist_y.abs()
  } else {
      center_dy
  };
  ```

#### [WARN-2] packages/rust/src/layout.rs:544-551

#### [WARN-3] packages/rust/src/layout_test.rs:1050-1063
- **Category**: Null/Boundary Handling
- **Description**: The test assertion allows a `COMBO_PADDING` tolerance on right/bottom overflow (`right <= parent_right + COMBO_PADDING`), which is 20px. This tolerance is quite generous and may mask regressions where the re-clamp logic is not working correctly. If the re-clamp is effective, the position should be clamped such that only the child's width/height can cause overflow (not position), and the overflow should be at most `rect.width - (max_x - min_x)` or `rect.height - (max_y - min_y)`, not a blanket `COMBO_PADDING`.
- **Suggestion**: Replace the blanket `COMBO_PADDING` tolerance with a computed tolerance based on the child rect size vs available parent space. For example, a child that is larger than the parent inner area will overflow by `child_width - inner_width`, and the tolerance should account for that specifically rather than a fixed padding value.

In practice this is unlikely to cause visible issues due to the iterative nature of the algorithm.
